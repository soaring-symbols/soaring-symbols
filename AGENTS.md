# AGENTS.md

Instructions for AI coding agents working in this repository. Human-facing docs live in `README.md`, `CONTRIBUTING.md` and `API.md`; read `CONTRIBUTING.md` before adding or changing any airline.

## Project

Soaring Symbols is an npm package (`soaring-symbols`) that ships a curated collection of airline logos, icons and tail designs as SVG, plus a small JS API to look them up.

- `airlines.json` — the airline catalog (source of truth for metadata), holding only hand-written fields, `slug` included. Sorted alphabetically by `name`. The build adds `assets` to every entry of the published `dist/airlines.json`, `history` to those with older marks, a `slug` to each renamed one's `former` names and `predecessors` to those that carried on a defunct airline (`utils/catalog.js`), so the repo copy never has them.
- `alliances.json` — the alliance catalog: one entry per alliance `airlines.json` may name in `alliance` (`name` must be in the schema's `$defs/alliance` enum, and `validateAlliances` in `utils/schema.js` requires an entry for each), sorted by name, with `slug`, `website`, `founded`, `defunct`/`ceased` and `branding`. Its schema, `alliances.schema.json`, refers to `airlines.schema.json`'s definitions. Marks live in `alliances/<slug>/` (`ALLIANCES_DIR`), only `icon` and `logo` (`findAllianceFileProblems`), with `history/<year>/` as for an airline; an alliance may have no folder yet, but every folder needs an alliance, and an alliance with SVGs needs `branding.primary_color` (`findMissingColors`). `lint-svg.js` lints them with the alliance's name as `<title>`; the build publishes `dist/alliances.json` (`publishAlliances` in `utils/catalog.js`, adding `assets` and `history`) and `dist/alliances/`, and `index.js` exports `listAlliances`, `getAlliance` and `getAllianceAssetPath`.
- `airports.json` — the latitude and longitude of every hub the catalog lists, by IATA code (`{ "HAN": { "lat": 21.22, "lon": 105.81 } }`), for maps and the website's globe. `sync-data.js` adds a new hub's from Wikidata (P625, the same item it reads the IATA code from); one Wikidata lacks is added by hand. `generate` sorts it, drops airports no airline lists and stops on a hub without coordinates (`utils/airports.js`); the build publishes it minified as `dist/airports.json`.
- `airlines.schema.json` — JSON Schema (draft 2020-12) for `airlines.json`. The root schema describes the repo copy; `$defs/published` the built one, which also requires `assets` (and allows `former[].slug`, `history` and `predecessors`). `generate.js` and `build.js` refuse data that fails it, and `scripts/test.js` checks both copies. Adding or changing a field means updating the schema, `index.d.ts`, `CONTRIBUTING.md` and `API.md` together.
- `assets/<slug>/` — SVGs per airline. `<slug>` is the entry's `slug`, which must equal `slugify(name, { lower: true, strict: true })` (`toSlug` in `utils/index.js`): `generate` fills it in when missing and `validateAirlines` rejects any other value, so it is never chosen by hand. Slugs are unique across all airlines, defunct included, and `parent`/`marks` point at them (`parent` is the group whose brand an airline flies under, else its largest airline shareholder: "Subsidiaries and shared logos" in `CONTRIBUTING.md`). An airline with `marks` has no folder: `build.js` copies the named airline's SVGs to `dist/assets/<slug>/` with its own `<title>`, and the published catalog reports their `assets`.
  - `history/<year>/` (optional) — the marks an airline used before its current ones, one folder per year a mark was introduced, with the same file names; `assets/<slug>/` always holds the current marks. `findHistoryProblems` (`utils/index.js`) checks the folders in `generate`, `getAssetDirs` lists the current folder plus each year so `lint-svg.js`, the derived monos and the build treat them like any asset folder, and `getAirlineHistory` describes them (`since`, `name` from the mark's `<title>`, `assets`, oldest first); `publishCatalog` adds `until` for the published `history`: the next mark's `since`, or for the last one the airline's hand-written `branding.since`, which `findOpenHistory` (`utils/schema.js`) requires once there is history. Airlines with `marks` get no history. An older mark's `<title>` may keep the name it was used under, if it is a name in `former` (`ruleTitle` in `scripts/lint/rule-structure.js`); everywhere else it is the current name. `getAssetPath(airline, type, { since })` returns a history file. History is for a new logo under the same name.
  - Renames and mergers: each entry is one airline, not one brand. A rename changes `name`, adds the old one to `former` (`{ name, until }`, plus any code or callsign that changed with it) and takes the new name's slug (folder renamed with `git mv`); the build adds each old name's slug to its `former` item, copies the current files to `dist/assets/<old slug>/` for each old slug a release has shipped (`copyFormerSlugs` in `build.js`, reading `published-slugs.json`, which `release.js` adds every released slug to) and `getAirline` resolves them, so it is a patch release. New codes under the same name also go in `former` (`{ iata?, icao?, callsign?, until }`); `getAirline` matches a former code only after every current code, slug and name. A brand that flies under its parent's codes keeps its entry and takes them (Hawaiian Airlines under Alaska Airlines), its own old codes in `former`: `findDuplicateCodes` allows codes shared with the `parent` and `getAirline` returns the parent for them. An IATA controlled duplicate (one code given to two airlines, `SL*` on IATA's code search) is allowed when every holder but one has `iata_duplicate: true`, and `getAirline` returns the one without it (SL: Thai Lion Air, not SAS Connect), and the starred one for the code with the asterisk (`SL*`: SAS Connect). `findDuplicateSlugs` counts the old slugs too. Only a merger, a refounding or a move into or out of a group's brand (Jetstar Pacific → Pacific Airlines) gets a new entry, the old one defunct with `successor`; `findBrokenReferences` (`utils/schema.js`) rejects a `successor` that isn't another airline or loops back, and the build publishes the reverse as `predecessors`. A name reused by an unrelated airline (Pan Am) is not decided yet, so ask first. "When an airline changes" in `CONTRIBUTING.md` sums up every case.
  - `icon.svg`, `logo.svg`, `tail.svg` are the color versions; `*-mono.svg` are the monochrome variants: for single-color assets the build derives them into `dist/assets` (the repo has none, and `npm run generate` deletes any committed copy); for multi-color ones they are optional and hand-made.
- `index.js` — ESM library entry (`listAirlines`, `getAirline`, `findAirlines`, `getAssetPath`, `listAlliances`, `getAlliance`, `getAllianceAssetPath`). It only reads `airlines.json` and `alliances.json` (no Node built-ins), so it stays browser-safe. Types in `index.d.ts` — keep them in sync, and keep `API.md` (including its migration guide) in step with any API change.
- `utils/index.js` — repo tooling only (not published): `toSlug`, the history helpers above, `getAirlineAssets` (detects color/mono files and colors from the SVGs on disk, counting the mono a single-color asset gets at build), `writeDerivedMonos` (used by the build), `removeDerivedMonos` (used by `generate`), and for the alliances `ALLIANCES_DIR`, `ALLIANCE_TYPES` and `findAllianceFileProblems`; `MARK_DIRS` lists both folders of marks (`assets`, `alliances`) for the tools that walk them all.
- `utils/catalog.js` — repo tooling only: `normalizeCatalog` and `normalizeAlliances` (the repo shape `generate.js` writes: sorted by name, keys in schema order, colors as six-digit lowercase hex, missing slugs filled in), `publishCatalog` (adds `former[].slug`, `assets`, `history` and `predecessors` for `build.js`) and `publishAlliances` (adds `assets` and `history`).
- `utils/airports.js` — repo tooling only: `hubCodes`, `normalizeAirports` (the shape `generate.js` writes) and `findAirportProblems` (a hub without coordinates, or a malformed entry).
- `utils/schema.js` — repo tooling only: compiles `airlines.schema.json` and `alliances.schema.json` with Ajv and exports `validateAirlines` (schema plus the checks it can't express: slugs, unique codes among active airlines except a brand's and its parent's and IATA's controlled duplicates, `former` (never the current name or codes, oldest first), `alliance_history` (oldest first), `branding.since` for history, and `parent`/`marks`/`successor` references; `{ published: true }` for the built copy), `validateAlliances`, `isValidField` and the field order entries are written in (`airlineFields`, `allianceFields`). Kept apart so the SVG tooling doesn't load Ajv.
- `svg-validator.js` — browser-safe validator exported as `soaring-symbols/svg-validator`, used by the website's validate page. It runs the same checks as `lint-svg.js` (every rule's check lives in `scripts/lint/validators.js`, which the build inlines; the rules only add the fixes), tagged with a `group`, a `level` (`warning` for the rules `--check` never fails on) and `fixable` (`true`, the `fixSvg` option `--fix` needs, or `false`; `npm test` checks the samples' fixable failures get fixed).
- `svg-fixer.js` — `lint-svg.js --fix` for the browser, exported (ESM only) as `soaring-symbols/svg-fixer` for the website's validate page. Both run `fixSvg` in `scripts/lint/fix.js`; esbuild bundles it with `svgo/browser` and `@resvg/resvg-wasm` (`scripts/lint/resvg-browser.js`, an optional peer dependency pinned to the `@resvg/resvg-js` version so render checks agree). `npm test` fixes broken samples and every asset both ways and fails on any difference. Rule code must stay free of Node built-ins.
- `scripts/` — tooling: `build.js`, `optimize.js`, `check-optimized.js` (and `lint-svg.js --changed`, which pick files with `scripts/lint/changed.js`), `generate.js`, `lint-svg.js` (+ rules in `scripts/lint/`, listed in `rules.js`; `rule-optimize.js` runs SVGO first, for the problems only it fixes; geometry runs apart in `rule-geometry.js`, measured with `@resvg/resvg-js` since jsdom has no `getBBox()`), `sync-data.js` (+ Wikipedia helpers in `scripts/sync/`), `test.js`, `release.js` (+ `purge-cdn.js` and `release-notes.js`).
- `dist/` — build output (git-ignored), the only code that is published.

## Commands

Node ≥ 20.12 is required (`index.js` uses JSON import attributes, the release tooling `Dirent.parentPath`); CI uses Node 24. Dependencies are tracked in both `package-lock.json` and `bun.lock`; Husky hooks call `bunx`.

- `npm run optimize -- <files>`: experimental; optimize SVGs in place with the project's SVGO config (`svgo.config.mjs`) at three decimals, or four or five when resvg renders the result differently from the original or the artwork leaves a viewBox edge it was on or fails a geometry check it passed (a result at four or five is rounded again at fewer decimals when that keeps it) (`scripts/optimize.js`, sharing `optimizeSvg` in `scripts/lint/optimize.js` with `--fix`; `optimize:check` uses its `optimizeAt` and `precisionOf`). It prints any bounding box value that changed at three decimals: report those to the maintainer and never commit optimized SVGs without having the results looked at.
- `npm run optimize:check`: exit 1 if `svgo.config.mjs`, at the precision the file is written with (its longest decimals, three to five), would still make an SVG changed since `origin/main` (committed, uncommitted or untracked) more than 10% smaller, i.e. it was never optimized with SVGO or SVGOMG; a file kept at four decimals passes, though `npm run optimize` may write three; `-- --base <ref>` or file arguments pick other files. CI runs it on each PR's changed SVGs only, since many older SVGs are still over the limit (#54).
- `node scripts/lint-svg.js --fix`: lint and rewrite fixable SVG issues in place (`npm run lint:svg` is the same without writing).
- `node scripts/lint-svg.js --changed --fix`: experimental; lint and fix only the SVGs added or changed since `origin/main` (`--base <ref>`, or list the files instead), leaving the others alone. It ends by asking for a full `--check` or the validator page, which CI still runs on every SVG.
- `node scripts/lint-svg.js --check`: lint without writing; exit 1 if any file has an issue `--fix` would handle or a hard error (warnings never fail). Used by CI.
- `npm run generate`: delete committed `-mono.svg` of single-color assets, re-sort `airlines.json`, fill in missing slugs and drop the generated `former[].slug`, `assets`, `history` and `predecessors`, check each slug has its folder and well-formed `history/` year folders, delete a stray `AIRLINES.md`, validate the catalog as it would be published, tidy and check `airports.json`, and do the same for `alliances.json` and `alliances/` (every folder needs an alliance, an alliance may have no folder yet). It writes nothing unless every check passes.
- `npm run build`: `lint:svg` + `generate` (via `prebuild`; that lint only reports, so use `node scripts/lint-svg.js --check` to fail on issues), then build `dist/` (ESM, CJS, type declarations, validator bundle, fixer bundle, minified `airlines.json`, `alliances.json` and `airports.json`, `assets/` and `alliances/` plus derived `-mono.svg`, shared marks and former-slug copies).
- `npm run lint` and `npm run format:check`: ESLint and Prettier (`**/*.{js,ts}`); CI fails on either, and `npm run lint:fix` / `npm run format` fix them. The pre-commit hook runs them on staged `*.js` only.
- `npm test`: build, then run `scripts/test.js` (`node:test`) against the ESM and CJS builds in `dist/`.
- `npm run sync:data`: compare `iata`, `icao`, `callsign`, `hubs`, `alliance`, `founded` and `defunct`/`ceased` with each airline's English Wikipedia infobox, add to `former` the names its founding dates say it flew under ("1968 (as Sahakol Air)") when a later name dates their end, add the coordinates of hubs new to `airports.json`, and print the differences; `-- --write` applies them and runs `generate`. Needs network.
- `npm run release`: cut a release (see below).

## Adding or updating an airline

1. Put the SVGs in `assets/<slug>/` following `CONTRIBUTING.md`: optimized with `npm run optimize` (never SVGO's defaults, which drop `role="img"`), `role="img"`, `xmlns`, `<title>Airline Name</title>` as the first child, `viewBox="0 0 64 64"` for logos and `0 0 24 24` for icons and tails, six-digit lowercase hex colors only, no `transform`, no scripts.
2. Add the base entry to `airlines.json` (`name`, `slug`, `iata`, `icao`, `country`, `website`, `branding.primary_color`, plus optional fields from `CONTRIBUTING.md`). A hub not yet in `airports.json` needs its coordinates there (Wikidata P625), or `generate` stops.
3. Run `node scripts/lint-svg.js --fix`, then `npm run generate`, and commit the SVGs together with `airlines.json` and whatever `generate` rewrote (`airports.json`, `alliances.json`).
4. Run `npm test`, `npm run lint` and `npm run format:check`, then check `git status` is clean: CI fails a pull request whose tooling output is not committed.

For a new logo under the same name, the new SVGs replace the files in `assets/<slug>/` and the old ones, if kept, move to `assets/<slug>/history/<year introduced>/` (see "Older Marks" in `CONTRIBUTING.md`); in `airlines.json`, set `branding.since` to the year the new marks came in (required once the airline has history) and change `branding.primary_color` only if it changed.

## Gotchas

- `lint-svg.js` checks what an optimized SVG looks like (`scripts/lint/rule-format.js`), not that it matches one SVGO version: most older SVGs came from SVGOMG on SVGO 2.x and differ from today's output by a few bytes. The SVGs a PR adds or changes must also be optimized (`check-optimized.js`), with any SVGO-based tool: the check allows up to 10% that `npm run optimize` would still remove, since SVGOMG's output stays under 7%. When a file has a problem only SVGO fixes (design-tool data, long decimals or `-0`, non-hex colors, `<style>`, transforms), `lint-svg.js --fix` runs `svgo.config.mjs` on it before the other rules (`scripts/lint/rule-optimize.js`), keeping the result only when resvg renders it like the original. `optimizeSvg` tries three decimals first, keeping them only when resvg renders the result like the original, the artwork stays on every viewBox edge and size it matched at three decimals (within 0.0005, so 64.000 stays 64.000) and the geometry checks pass as before: rounding at three adds up to 0.001-0.05 on about a fifth of the SVGs, which `rule-geometry.js` still calls exact under 0.01. Both tests are measured against the viewBox, not the input, so optimizing a result again changes nothing, and `optimize:check` passes what `npm run optimize` writes. The lint rule allows up to five decimals, so older files pass.
- `lint-svg.js` exits 0 even when it finds issues unless you pass `--check` — read its output, or use `--check` when the exit code matters. Some rules only warn. Of those, `--fix` flattens nested groups when resvg renders the result like the original (`scripts/lint/fix-structure.js`). Merging neighbouring paths of the same color, in single- and multi-color SVGs, is experimental and opt-in (`--fix --merge-paths`, same render check): never run it unasked, and have the result looked at. Shapes of one color with another color between them, and geometry, are left for the editor. Without `--changed`, `--base` or file arguments, `lint-svg.js` lints every SVG; any of them (even `--base <ref>` alone) limits it to those files and prints a `🧪 EXPERIMENTAL` line first, so verify a change across the collection with a plain `node scripts/lint-svg.js --check`, never a scoped run. Broken SVGs that `lint-svg.js` skips until they are redrawn or refit are listed in `EXCLUDE_FILES` in `scripts/lint/exclude.js`.
- `generate.js` rewrites `airlines.json` from scratch (4-space JSON) and orders each entry's keys as `airlines.schema.json` lists them. `former[].slug`, `assets`, `history` and `predecessors` exist only in `dist/airlines.json`: read them there after a build. `npm run build` / `npm test` also run it, so a build can leave the working tree dirty.
- The CJS build is produced by two regex replacements in `scripts/build.js` (`transformToCJS`): the `airlines.json` and `alliances.json` imports (one regex) and the single `export { ... }` list. It throws if any other `import`/`export` is left, so adding an import to `index.js` means updating it.
- `sync-data.js` treats Wikipedia as a hint, never an authority: it only applies a change when the data still validates (so a code that would clash with another active airline is held back for review), and its pull request is always reviewed by hand. A monthly workflow (`.github/workflows/sync-data.yml`) runs it with `--write --summary <file>` and opens the `chore/sync-airline-data` pull request; nothing is merged automatically. Airlines whose name leads to the wrong page are mapped in `PAGE_TITLES`, rejected values go in `IGNORE`, both at the top of the script. Wikipedia rate-limits hard: keep requests batched.
- `svg-validator.js` must stay free of Node-only imports, and every helper it uses from `scripts/lint/validators.js` must be a top-level `export function` so the build can inline it (its constants stay unexported). A new lint rule puts its check in `validators.js`, gets a row in `runSvgValidations` and is listed in `scripts/lint/rules.js` (in `DOM_RULES` or `STRING_RULES`, and in `BROWSER_CHECKS` with that row's label, plus `warning: true` for a rule that only warns); `npm test` fails if a rule has no browser check (or a check no rule), or if an SVG passes `lint-svg.js` but not the browser checks. `row()` defaults `fixable` to `true`: pass `false` (or the `fixSvg` option it needs) for a rule `--fix` can't fix, or the website offers a fix that does nothing.

## Conventions

- Commits follow Conventional Commits and are checked by commitlint, e.g. `feat: add Vietravel Airlines`, `fix(build): ...`, `chore(release): v0.2.1`.
- The roadmap for the collection and every integration (npm, CDN, the website's API, Raycast, plugins, packages) lives only in this repository's `README.md`. The website's README tracks only plans for the site itself and links here, so update the roadmap in one place.

## Releasing

Versions are plain 0.x, without prerelease labels: `patch` for compatible changes (new airlines and assets, SVG fixes, additions to the API or data) and `minor` for breaking changes to the API or the `airlines.json` shape. Run `npm run release -- [bump]` from a clean, up-to-date `main`; `bump` is `patch` by default, or `minor`/`major`/an exact version like `0.2.0`, and `--dry-run` previews. The script in `scripts/release.js` tests the package, bumps the version in `package.json`, publishes to npm under `latest`, adds the airline slugs it shipped to `published-slugs.json`, purges jsDelivr's cache of the files that changed since the previous release (`scripts/purge-cdn.js`), commits `package.json`, `package-lock.json` and `published-slugs.json` as `chore(release): v<version>` and tags that commit `v<version>` (an annotated tag), without pushing. Never run it unless the maintainer asks for a release.

Patch releases go out weekly, by hand, in a week with something users see since the previous tag (new airlines or marks, SVG or data fixes); a week without skips the release. `node scripts/release-notes.js` shows what is waiting. Breaking changes, removing an airline above all (`getAirline()` stops finding it and its files disappear from the release line), wait for the next minor release: their pull requests stay open with the `breaking` label, and a patch release may say in its notes that the removal is coming. When `main` already holds a breaking commit (`!` or `BREAKING CHANGE`, which `release-notes.js` lists under Breaking changes), the next release is `minor`, never the default `patch`. The one exception is a takedown request (a trademark owner asking for its marks to go), which ships in the next patch with the reason in its notes. Minor releases are rare, gathering what has waited, since each one moves the Raycast extension and the Figma plugin to a new release line ("Keeping releases compatible" below).

Pushing the tag (`git push --atomic origin main v<version>`, the maintainer's call) runs `.github/workflows/release.yml`, which publishes a GitHub release titled `v<version>` with only a compare link to the previous tag, and never touches a release that already exists. Nothing is released automatically or on a schedule; that is not decided yet.

The release notes are written afterwards, when the maintainer asks: start from the draft `node scripts/release-notes.js --to v<version>` prints (the commits since the previous tag, grouped into breaking changes, airlines, features and fixes), then rewrite it for readers of the package the way the existing releases read: a one-sentence summary first, before any section, saying what is new for a patch ("Three new airlines: Air Arabia Abu Dhabi, Air Arabia Egypt and Air Arabia Maroc.") and what breaks and what readers must do for a minor (the website's changelog shows it under the version, and feed readers see it first); then `###` sections (Breaking changes, Airlines, Features, Fixes, any of them), one line per change described by its net result (an airline added and its data fixed in a later commit is one line, with its codes; a change made and undone is left out), PR numbers kept, internal tooling only when contributors notice it, and the compare link last. Add an `### Ecosystem` section, after the others, for what reached users outside the package since the previous release: the website and its API deploy as they merge, so a change there goes in the first release after it went live; the Raycast extension, the Figma plugin and any other app or plugin only once, in the first release after it is officially published on its store (not while in review); their later updates are not mentioned. Show the notes to the maintainer, then set them with `gh release edit v<version> --notes-file <file>`. Tags and GitHub releases start at v0.2.0: the `0.1.0-alpha` versions have none, and v0.2.0's notes sum up everything before it.

The purge waits until jsDelivr resolves the release line (`@0.3`) to the new version, then purges each changed file of `dist/` under the line and the bare package, so links like `soaring-symbols@0.3/dist/assets/<slug>/logo.svg` serve the new file at once instead of after up to 12 hours. Exact-release links never need it. A failed purge only warns; rerun it with `node scripts/purge-cdn.js --since <previous version>` (`--dry-run` lists the files). Clients' own caches, such as a browser's or Raycast's, can still keep a line URL for up to 7 days, which is why the Raycast extension loads files from the exact release.

### Keeping releases compatible

The Raycast extension ([soaring-symbols/raycast](https://github.com/soaring-symbols/raycast)) and the Figma plugin ([soaring-symbols/figma](https://github.com/soaring-symbols/figma)) read `airlines.json` and the SVGs from the published package through jsDelivr, each pinned to one release line (e.g. `soaring-symbols@0.2`). Every patch release reaches them automatically; a minor release does not until they are updated. So:

- Prefer additive changes, released as a patch: add a new field or file and keep the old one, so existing consumers keep working. Remove or rename something only in a later minor release, and say so in the release notes.
- Treat anything that can break a reader of the previous release as breaking and release it as a minor: removing or renaming a field in `airlines.json`, changing a field's meaning or type, moving or renaming files under `assets/`, or changing the exported functions.
- Before a minor release, prepare the extension and plugin updates for the new line (each one's `AGENTS.md` lists the steps) so they can be published right after the release.
