# AGENTS.md

Instructions for AI coding agents working in this repository. Human-facing docs live in `README.md`, `CONTRIBUTING.md` and `API.md`; read `CONTRIBUTING.md` before adding or changing any airline.

## Project

Soaring Symbols is an npm package (`soaring-symbols`) that ships a curated collection of airline logos, icons and tail designs as SVG, plus a small JS API to look them up.

- `airlines.json` — the airline catalog and source of truth for metadata, sorted by `name`, holding only hand-written fields (`slug` included). The build (`utils/catalog.js`) adds to the published `dist/airlines.json` `assets` on every entry, `history` for older marks, a `slug` on each `aliases` item and on each renamed airline's `former` names, and `predecessors` for airlines that carried on a defunct one; the repo copy never has them.
- `alliances.json` — the alliance catalog, sorted by name: one entry (`slug`, `website`, `founded`, `defunct`/`ceased`, `branding`) per alliance `airlines.json` may name in `alliance` (`name` must be in the schema's `$defs/alliance` enum, and `validateAlliances` in `utils/schema.js` requires an entry for each). Its schema, `alliances.schema.json`, refers to `airlines.schema.json`'s definitions. Marks live in `alliances/<slug>/` (`ALLIANCES_DIR`), only `icon` and `logo` (`findAllianceFileProblems`), with `history/<year>/` as for an airline; an alliance may have no folder yet, but every folder needs an alliance, and an alliance with SVGs needs `branding.primary_color` (`findMissingColors`). `lint-svg.js` lints them with the alliance's name as `<title>`; the build publishes `dist/alliances.json` (`publishAlliances` in `utils/catalog.js`, adding `assets` and `history`) and `dist/alliances/`; `index.js` exports the alliance functions.
- `airports.json` — latitude and longitude of every hub the catalog lists, by IATA code (`{ "HAN": { "lat": 21.22, "lon": 105.81 } }`), for maps and the website's globe. `sync-data.js` adds a new hub's from Wikidata (P625, on the item it reads the IATA code from); one Wikidata lacks is added by hand. `generate` sorts it, drops airports no airline lists and stops on a hub without coordinates (`utils/airports.js`); the build publishes it minified as `dist/airports.json`.
- `airlines.schema.json` — JSON Schema (draft 2020-12) for `airlines.json`: the root describes the repo copy, `$defs/published` the built one, which also requires `assets` and allows the other published fields. `generate.js` and `build.js` refuse data that fails it; `scripts/test.js` checks both copies. Adding or changing a field means updating the schema, `index.d.ts`, `CONTRIBUTING.md` and `API.md` together.
- `assets/<slug>/` — SVGs per airline. `<slug>` must equal `slugify(name, { lower: true, strict: true })` (`toSlug` in `utils/index.js`), so it is never chosen by hand: `generate` fills it in when missing and `validateAirlines` rejects any other value. Slugs are unique across all airlines, defunct included, and `parent`/`marks` point at them (`parent` is the group whose brand an airline flies under, else its largest airline shareholder: "Subsidiaries and shared logos" in `CONTRIBUTING.md`). An airline with `marks` has no folder: `build.js` copies the named airline's SVGs to `dist/assets/<slug>/` with its own `<title>`, and its published `assets` report them. `marks` may name an airline that itself takes types with `marks_types` (LATAM Cargo Brasil → LATAM Cargo Chile → LATAM Airlines Chile's icon), one step only (`findBrokenReferences` in `utils/schema.js`); `copySharedMarks` copies those after the airlines they borrow from, and `publishCatalog` resolves their `assets` through the chain. With `marks_types` (e.g. `["icon"]`, a cargo brand with its own logo and its parent's icon; see "Cargo airlines") only those types are copied, the airline keeps a folder for the others, and `generate` stops on a file of a listed type in it.
  - `history/<year>/` (optional) — marks used before the current ones, which `assets/<slug>/` always holds: one folder per year a mark was introduced, same file names. History is for a new logo under the same name. `findHistoryProblems` (`utils/index.js`) checks the folders in `generate`; `getAssetDirs` lists the current folder plus each year, so `lint-svg.js`, the derived monos and the build treat them like any asset folder; `getAirlineHistory` describes them (`since`, `name` from the mark's `<title>`, `assets`, oldest first), and `publishCatalog` adds `until`: the next mark's `since`, or for the last one the hand-written `branding.since`, which `findOpenHistory` (`utils/schema.js`) requires once there is history. Airlines with `marks` get no history. An older mark's `<title>` may keep the name it was used under if that name is in `former` (`ruleTitle` in `scripts/lint/rule-structure.js`); everywhere else it is the current name. `getAssetPath(airline, type, { since })` returns a history file.
  - Aliases ("Aliases" in `CONTRIBUTING.md`): `name` is the full name (Swiss International Air Lines); a shorter name the airline uses now (SWISS, THAI) goes in `aliases` (`[{ name }]`), one it stopped using in `former`. The build adds each alias's slug, `getAirline` finds the airline by the alias and its slug (after names, before former codes), `copyFormerSlugs` copies the current files to an alias slug a release shipped, and `findDuplicateSlugs` counts alias slugs, so an entry that used the short name can take its full one as a patch. `findAliasProblems` (`utils/schema.js`) rejects an alias that is the name, a former name or repeated.
  - Renames and mergers: each entry is one airline, not one brand. "Renames and mergers" in `CONTRIBUTING.md` explains them, and "When an airline changes" sums up every case.
    - A rename changes `name`, adds the old one to `former` (`{ name, until }`, plus any code or callsign that changed with it) and takes the new name's slug (folder renamed with `git mv`). The build adds each old name's slug to its `former` item and copies the current files to `dist/assets/<old slug>/` for each old slug a release shipped (`copyFormerSlugs` in `build.js`, reading `published-slugs.json`, to which `release.js` adds every released slug); `getAirline` resolves them, so it is a patch release. `findDuplicateSlugs` counts the old slugs too.
    - New codes under the same name also go in `former` (`{ iata?, icao?, callsign?, until }`); `getAirline` matches a former code only after every current code, slug and name.
    - A brand that flies under its parent's codes keeps its entry and takes them (Hawaiian Airlines under Alaska Airlines), its own old codes in `former`: `findDuplicateCodes` allows codes shared with the `parent`, and `getAirline` returns the parent for them.
    - An IATA controlled duplicate (one code given to two airlines, `SL*` on IATA's code search) is allowed when every holder but one has `iata_duplicate: true`; `getAirline` returns the unstarred one for the code (SL: Thai Lion Air) and the starred one for the code with the asterisk (`SL*`: SAS Connect).
    - Only a merger, a refounding or a move into or out of a group's brand (Jetstar Pacific → Pacific Airlines) gets a new entry, the old one defunct with `successor`; `findBrokenReferences` (`utils/schema.js`) rejects a `successor` that isn't another airline or loops back, and the build publishes the reverse as `predecessors`.
    - A name reused by an unrelated airline (Pan Am) is not decided yet, so ask first.
  - `icon.svg`, `logo.svg`, `tail.svg` are the color versions; `logo.svg` is the horizontal lockup (or the only one), and the optional `logo-stacked.svg` (a fourth type in `assetTypes`/`ASSET_TYPES`) the airline's own vertical one, only beside it (`findLoneStackedLogos` in `utils/schema.js`); alliances have none. `*-mono.svg` are the monochrome variants: for single-color assets the build derives them into `dist/assets` (the repo has none, and `npm run generate` deletes any committed copy); for multi-color ones they are optional and hand-made.
  - `*-dark.svg` are the versions for dark backgrounds, derived into `dist/assets` after the monos (`writeDerivedDarks`, `darkSource` in `utils/index.js`) following brand guidelines, which show marks in white on dark: the color file for the types in `branding.dark_color` (current marks only; `generate` warns about colors under 3:1 against `#1e1e1e` but never stops on them), else the mono painted `#ffffff`, else (no mono yet) the color file when every color reaches 3:1, else none. The repo holds only hand-made ones, for an airline's own partial recolor (Ryanair: blue lettering white, harp yellow), drawn from what the airline shows on a dark background (one on a brand-colored background only when nothing else is known, said in the pull request so it can be checked later), never recolored by hand; an all-white version is a `-mono.svg`. `findDarkProblems` (run by `generate`) stops on a dark file without its color file, with another viewBox, identical to the color file, in one color or for a type in `branding.dark_color`.
- `index.js` — ESM library entry (`listAirlines`, `getAirline`, `findAirlines`, `getAssetPath`, `listAlliances`, `getAlliance`, `getAllianceAssetPath`). It reads only `airlines.json` and `alliances.json` (no Node built-ins), so it stays browser-safe. Keep its types in `index.d.ts` and `API.md` (including the migration guide) in step with any API change.
- `utils/index.js` — repo tooling only (not published): `toSlug`, the history helpers above, `getAirlineAssets` (detects color, mono and dark files and colors from the SVGs on disk, counting the mono and dark files the build will add), `writeDerivedMonos` and `writeDerivedDarks` (used by the build), `removeDerivedMonos` and `findDarkProblems` (used by `generate`), `ALLIANCES_DIR`, `ALLIANCE_TYPES` and `findAllianceFileProblems` for the alliances, and `MARK_DIRS` (`assets`, `alliances`) for the tools that walk all marks.
- `utils/catalog.js` — repo tooling only: `normalizeCatalog` and `normalizeAlliances` (the repo shape `generate.js` writes: sorted by name, keys in schema order, colors as six-digit lowercase hex, missing slugs filled in), and `publishCatalog` and `publishAlliances`, which add the published fields above for `build.js`.
- `utils/airports.js` — repo tooling only: `hubCodes`, `normalizeAirports` (the shape `generate.js` writes) and `findAirportProblems` (a hub without coordinates, or a malformed entry).
- `utils/schema.js` — repo tooling only, kept apart so the SVG tooling doesn't load Ajv: compiles both schemas with Ajv and exports `validateAirlines` (the schema plus what it can't express: slugs; unique codes among active airlines, except a brand's shared with its parent and IATA's controlled duplicates; `aliases` (never the name or a former one); `former` (never the current name or codes, oldest first); `alliance_history` (oldest first); `flag_carrier_countries` (must include `country`); `branding.since` for history; `findLoneStackedLogos`; `branding.dark_color` (each listed type has a color file, also checked for alliances; `findDarkColorWarnings` lists its colors under 3:1 on `#1e1e1e` for `generate` to print); and `parent`/`marks`/`successor` references; `{ published: true }` for the built copy), `validateAlliances`, `isValidField` and the field orders entries are written in (`airlineFields`, `allianceFields`).
- `svg-validator.js` — browser-safe validator exported as `soaring-symbols/svg-validator` for the website's validate page. It runs the same checks as `lint-svg.js` (each rule's check lives in `scripts/lint/validators.js`, which the build inlines; the rules only add the fixes), each tagged with a `group`, a `level` (`warning` for rules `--check` never fails on) and `fixable` (`true`, the `fixSvg` option `--fix` needs, or `false`; `npm test` checks the samples' fixable failures get fixed).
- `svg-fixer.js` — `lint-svg.js --fix` for the browser, exported (ESM only) as `soaring-symbols/svg-fixer` for the validate page. Both run `fixSvg` in `scripts/lint/fix.js`; esbuild bundles it with `svgo/browser` and `@resvg/resvg-wasm` (`scripts/lint/resvg-browser.js`; an optional peer dependency pinned to the `@resvg/resvg-js` version so render checks agree). `npm test` fixes broken samples and every asset both ways and fails on any difference. Rule code must stay free of Node built-ins.
- `scripts/` — tooling: `build.js`, `optimize.js`, `check-optimized.js` (it and `lint-svg.js --changed` pick files with `scripts/lint/changed.js`), `generate.js`, `lint-svg.js` (rules in `scripts/lint/`, listed in `rules.js`; `rule-geometry.js` runs apart, measuring with `@resvg/resvg-js` since jsdom has no `getBBox()`), `sync-data.js` (Wikipedia helpers in `scripts/sync/`), `test.js`, `release.js` (+ `purge-cdn.js` and `release-notes.js`).
- `dist/` — build output (git-ignored), the only code that is published.

## Commands

Node ≥ 20.12 is required (`index.js` uses JSON import attributes, the release tooling `Dirent.parentPath`); CI uses Node 24. Dependencies are tracked in both `package-lock.json` and `bun.lock`; Husky hooks call `bunx`.

- `npm run optimize -- <files>`: optimize SVGs in place with `svgo.config.mjs` at three decimals, or four or five when three would change the artwork (see Gotchas) (`scripts/optimize.js`, sharing `optimizeSvg` in `scripts/lint/optimize.js` with `--fix`; `optimize:check` uses its `savingOf` and `MAX_SAVING`). `-- --precision=4` (or `5`) keeps at least that many decimals, as for `--fix`. It prints any bounding box value that changed at three decimals (`bboxChanges`, which `--fix` lists too): report those to the maintainer and never commit optimized SVGs without having the results looked at.
- `npm run optimize:check`: exit 1 if `svgo.config.mjs`, at the file's own precision (its longest decimals, three to five), would still make an SVG changed since `origin/main` (committed, uncommitted or untracked) more than 10% smaller, i.e. it was never optimized with SVGO or SVGOMG; a file kept at four decimals passes, though `npm run optimize` may write three. `-- --base <ref>` or file arguments pick other files. CI runs it on each PR's changed SVGs only, since many older SVGs are still over the limit (#54).
- `node scripts/lint-svg.js --fix`: lint and rewrite fixable SVG issues in place (`npm run lint:svg` does the same without writing). It optimizes only a file with a problem only SVGO fixes, and then lists the bounding box values that moved, as `npm run optimize` does; `--precision=4` (or `5`, written with `=`) makes SVGO keep at least that many decimals, for a file that rounds 0.0005 off its edges or center at three, which the geometry checks still pass (the website's validate page suggests it for those). On the files it is given (file arguments or `--changed`), it also warns about one `optimize:check` would fail and points to `npm run optimize`, which optimizes clean files too; a full run doesn't, since many older SVGs are still over the limit (#54).
- `node scripts/lint-svg.js --changed --fix`: experimental; lint and fix only the SVGs added or changed since `origin/main` (`--base <ref>`, or list the files instead). It ends by asking for a full `--check` or the validator page, which CI still runs on every SVG.
- `node scripts/lint-svg.js --check`: lint without writing; exit 1 on any issue `--fix` would handle or a hard error (warnings never fail). Used by CI.
- `npm run generate`: delete committed `-mono.svg` of single-color assets, re-sort `airlines.json`, fill in missing slugs and drop the published-only fields, check each slug has its folder and well-formed `history/` year folders, check hand-made `-dark.svg` files (`findDarkProblems`), delete a stray `AIRLINES.md`, validate the catalog as it would be published, tidy and check `airports.json`, and do the same for `alliances.json` and `alliances/`. It writes nothing unless every check passes.
- `npm run build`: `lint:svg` + `generate` (via `prebuild`; that lint only reports, so use `node scripts/lint-svg.js --check` to fail on issues), then build `dist/` (ESM, CJS, type declarations, validator and fixer bundles, minified `airlines.json`, `alliances.json` and `airports.json`, `assets/` and `alliances/` plus derived `-mono.svg` and `-dark.svg`, shared marks and former-slug copies).
- `npm run lint` and `npm run format:check`: ESLint and Prettier (`**/*.{js,ts}`); CI fails on either, and `npm run lint:fix` / `npm run format` fix them. The pre-commit hook runs them on staged `*.js` only.
- `npm test`: build, then run `scripts/test.js` (`node:test`) against the ESM and CJS builds in `dist/`.
- `npm run sync:data`: compare `iata`, `icao`, `callsign`, `hubs`, `alliance`, `founded` and `defunct`/`ceased` with each airline's English Wikipedia infobox, add to `former` the names its founding dates say it flew under ("1968 (as Sahakol Air)") when a later name dates their end, add the coordinates of hubs new to `airports.json`, and print the differences; `-- --write` applies them and runs `generate`. Needs network.
- `npm run release`: cut a release (see below).

## Adding or updating an airline

1. Put the SVGs in `assets/<slug>/` following `CONTRIBUTING.md`: optimized with `npm run optimize` (never SVGO's defaults, which drop `role="img"`), `role="img"`, `xmlns`, `<title>Airline Name</title>` as the first child, `viewBox="0 0 64 64"` for logos and `0 0 24 24` for icons and tails, six-digit lowercase hex colors only, no `transform`, no scripts.
2. Add the base entry to `airlines.json` (`name`, `slug`, `iata`, `icao`, `country`, `website`, `branding.primary_color`, plus optional fields from `CONTRIBUTING.md`). A hub not yet in `airports.json` needs its coordinates there (Wikidata P625), or `generate` stops.
3. Run `node scripts/lint-svg.js --fix`, then `npm run generate`, and commit the SVGs together with `airlines.json` and whatever `generate` rewrote (`airports.json`, `alliances.json`).
4. Run `npm test`, `npm run lint` and `npm run format:check`, then check `git status` is clean: CI fails a pull request whose tooling output is not committed.

For a new logo under the same name, the new SVGs replace the files in `assets/<slug>/` and the old ones, if kept, move to `assets/<slug>/history/<year introduced>/` ("Older Marks (Logo History)" in `CONTRIBUTING.md`); set `branding.since` to the year the new marks came in (required once the airline has history) and change `branding.primary_color` only if it changed.

## Gotchas

- `lint-svg.js` checks what an optimized SVG looks like (`scripts/lint/rule-format.js`), not that it matches one SVGO version: most older SVGs came from SVGOMG on SVGO 2.x and differ from today's output by a few bytes. The SVGs a PR adds or changes must also be optimized (`check-optimized.js`), with any SVGO-based tool: the check allows up to 10% that `npm run optimize` would still remove, since SVGOMG's output stays under 7%. When a file has a problem only SVGO fixes (design-tool data, long decimals or `-0`, non-hex colors, `<style>`, transforms), `lint-svg.js --fix` runs `svgo.config.mjs` on it before the other rules (`scripts/lint/rule-optimize.js`), keeping the result only when resvg renders it like the original. `optimizeSvg` keeps three decimals only when resvg renders the result like the original, the artwork stays on every viewBox edge and size it matched at three decimals (within 0.0005, so 64.000 stays 64.000), each edge and center within 0.01 of the viewBox's stays as close as in the original (plus 0.0005, so 32 does not become 31.999), and the geometry checks pass as before; otherwise it tries four, then five, rounding a result at four or five again at fewer decimals when that keeps it, and when no precision keeps it, takes the closest. `rule-geometry.js` calls a measurement exact up to 0.0005 off, rounded to 1e-5 so resvg and the browser's `getBBox()` agree; a near miss within each check's tolerance is a warning, which never fails `--check`. Both tests are measured against the viewBox, not the input, so optimizing a result again changes nothing, and `optimize:check` passes what `npm run optimize` writes. The lint rule allows up to five decimals, so older files pass.
- `lint-svg.js` exits 0 even when it finds issues unless you pass `--check`: read its output, or use `--check` when the exit code matters. Some rules only warn; of those, `--fix` flattens nested groups when resvg renders the result like the original (`scripts/lint/fix-structure.js`). Merging neighbouring same-color paths, in single- and multi-color SVGs, is experimental and opt-in (`--fix --merge-paths`, same render check): never run it unasked, and have the result looked at. Shapes of one color with another color between them, and geometry, are left for the editor. `--changed`, `--base <ref>` (even alone) or file arguments limit `lint-svg.js` to those files and print a `🧪 EXPERIMENTAL` line first; without them it lints every SVG, so verify a change across the collection with a plain `node scripts/lint-svg.js --check`, never a scoped run. Broken SVGs it skips until they are redrawn or refit are listed in `EXCLUDE_FILES` in `scripts/lint/exclude.js`.
- `generate.js` rewrites `airlines.json` from scratch (4-space JSON, each entry's keys in `airlines.schema.json`'s order). The published-only fields (`aliases[].slug`, `former[].slug`, `assets`, `history`, `predecessors`) exist only in `dist/airlines.json`: read them there after a build. `npm run build` and `npm test` also run `generate`, so a build can leave the working tree dirty.
- The CJS build is two regex replacements in `scripts/build.js` (`transformToCJS`): one for the `airlines.json` and `alliances.json` imports, one for the single `export { ... }` list. It throws if any other `import`/`export` is left, so adding an import to `index.js` means updating it.
- `sync-data.js` treats Wikipedia as a hint, never an authority: it applies a change only when the data still validates (so a code that would clash with another active airline is held back for review). A monthly workflow (`.github/workflows/sync-data.yml`) runs it with `--write --summary <file>` and opens the `chore/sync-airline-data` pull request, always reviewed by hand and never merged automatically. Airlines whose name leads to the wrong page are mapped in `PAGE_TITLES`, rejected values go in `IGNORE`, both at the top of the script. Wikipedia rate-limits hard: keep requests batched.
- `svg-validator.js` must stay free of Node-only imports, and every helper it uses from `scripts/lint/validators.js` must be a top-level `export function` so the build can inline it (its constants stay unexported). A new lint rule puts its check in `validators.js`, gets a row in `runSvgValidations` and is listed in `scripts/lint/rules.js` (in `DOM_RULES` or `STRING_RULES`, and in `BROWSER_CHECKS` with that row's label, plus `warning: true` for a rule that only warns); `npm test` fails if a rule has no browser check (or a check no rule), or if an SVG passes `lint-svg.js` but not the browser checks. `row()` defaults `fixable` to `true`: pass `false` (or the `fixSvg` option it needs) for a rule `--fix` can't fix, or the website offers a fix that does nothing.

## Conventions

- Commits follow Conventional Commits and are checked by commitlint, e.g. `feat: add Vietravel Airlines`, `fix(build): ...`, `chore(release): v0.2.1`.
- The roadmap for the collection and every integration (npm, CDN, the website's API, Raycast, plugins, packages) lives only in this repository's `README.md`; the website's README tracks only the site's own plans and links here, so the roadmap is updated in one place.

## Releasing

Versions are plain 0.x, without prerelease labels: `patch` for compatible changes (new airlines and assets, SVG fixes, additions to the API or data), `minor` for breaking changes to the API or the `airlines.json` shape. Run `npm run release -- [bump]` from a clean, up-to-date `main`; `bump` is `patch` by default, or `minor`/`major`/an exact version like `0.2.0`, and `--dry-run` previews. `scripts/release.js` tests the package, bumps the version in `package.json`, publishes to npm under `latest`, adds the airline slugs it shipped to `published-slugs.json`, on a minor release moves the release line links in `README.md` and `API.md` (`soaring-symbols@0.<minor>`, never exact releases) to the new line (`scripts/release-line.js`; `npm test` fails when one points at another line, and docs that only explain a line write `@0.<minor>`), commits `package.json`, `package-lock.json`, `published-slugs.json` and those docs as `chore(release): v<version>` and tags that commit `v<version>` (annotated), without pushing. Never run it unless the maintainer asks for a release.

Patch releases go out weekly, by hand, in a week with something users see since the previous tag (new airlines or marks, SVG or data fixes); a week without skips the release. `node scripts/release-notes.js` shows what is waiting. Breaking changes, above all removing an airline (`getAirline()` stops finding it and its files disappear from the release line), wait for the next minor release: their pull requests stay open with the `breaking` label, and a patch release may say in its notes that the removal is coming. The one exception is a takedown request (a trademark owner asking for its marks to go), which ships in the next patch with the reason in its notes. When `main` already holds a breaking commit (`!` or `BREAKING CHANGE`, which `release-notes.js` lists under Breaking changes), the next release is `minor`, never the default `patch`. Minor releases are rare, gathering what has waited, since each one moves the Raycast extension and the Figma plugin to a new release line ("Keeping releases compatible" below).

Pushing the tag (`git push --atomic origin main v<version>`, the maintainer's call) runs `.github/workflows/release.yml`: it publishes a GitHub release titled `v<version>` with only a compare link to the previous tag (never touching a release that already exists) and, in a job of its own, purges jsDelivr's cache of the files changed since the previous release (`scripts/purge-cdn.js`). Nothing is released automatically or on a schedule; that is not decided yet.

The release notes are written afterwards, when the maintainer asks. Start from the draft `node scripts/release-notes.js --to v<version>` prints (the commits since the previous tag, grouped into breaking changes, airlines, features and fixes) and rewrite it for readers of the package, the way the existing releases read:

- A one-sentence summary first, before any section: what is new for a patch ("Three new airlines: Air Arabia Abu Dhabi, Air Arabia Egypt and Air Arabia Maroc."), what breaks and what readers must do for a minor (the website's changelog shows it under the version, and feed readers see it first).
- `###` sections (Breaking changes, Airlines, Features, Fixes, any of them), one line per change described by its net result (an airline added and its data fixed in a later commit is one line, with its codes; a change made and undone is left out), PR numbers kept, internal tooling only when contributors notice it, and the compare link last.
- An `### Ecosystem` section, after the others, for the major changes outside the package that come with the release's features, one line per app, for what users notice (no small fixes or polish). A package feature usually reaches the website and its API, the Raycast extension and the Figma plugin together, so their side of it goes in the notes of the release that ships the feature, even when it goes live a little later (update that release's notes then, not the next one's). The Raycast extension and the Figma plugin count once their update is published on their store, not while in review.

Show the notes to the maintainer, then set them with `gh release edit v<version> --notes-file <file>`. Tags and GitHub releases start at v0.2.0: the `0.1.0-alpha` versions have none, and v0.2.0's notes sum up everything before it.

The purge compares the new release's published `dist/` with the previous one's, waits (up to 20 minutes; jsDelivr has taken six to seven) until jsDelivr resolves the release line (`@0.<minor>`) and the bare package to the new version, then purges each changed file under both, so links like `soaring-symbols@0.<minor>/dist/assets/<slug>/logo.svg` serve the new file at once instead of after up to 12 hours; exact-release links never need it. A failed purge fails its job without touching the GitHub release: rerun the job, or run `node scripts/purge-cdn.js --since <previous version> [--version <version>]` from any checkout (`--dry-run` lists the files). Clients' own caches, such as a browser's or Raycast's, can still keep a line URL for up to 7 days, which is why the Raycast extension loads files from the exact release.

### Keeping releases compatible

The Raycast extension ([soaring-symbols/raycast](https://github.com/soaring-symbols/raycast)) and the Figma plugin ([soaring-symbols/figma](https://github.com/soaring-symbols/figma)) read `airlines.json` and the SVGs from the published package through jsDelivr, each pinned to one release line (`soaring-symbols@0.<minor>`, set as `DATA_LINE` in each). Every patch release reaches them automatically; a minor release does not until they are updated. So:

- Prefer additive changes, released as a patch: add a new field or file and keep the old one, so existing consumers keep working. Remove or rename something only in a later minor release, and say so in the release notes.
- A new value in a field that lists its values (an alliance in `AllianceName`, a type in `AssetType`) is new data, so it is a patch too: readers that don't know it yet keep showing the rest. Only TypeScript code that lists every value (`Record<AllianceName, …>`, an exhaustive `switch`) stops compiling, so the release notes name the new value.
- Treat anything that can break a reader of the previous release as breaking and release it as a minor: removing or renaming a field in `airlines.json`, changing a field's meaning or type, moving or renaming files under `assets/`, or changing the exported functions.
- Before a minor release, prepare the extension and plugin updates for the new line (each one's `AGENTS.md` lists the steps) so they can be published right after the release.
