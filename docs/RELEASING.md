# Releasing

How a soaring-symbols release is cut and announced, for the maintainer and for agents asked to help. `AGENTS.md` keeps the rules that apply to every change: never run `npm run release` unless the maintainer asks, and what counts as breaking ("Keeping releases compatible").

Versions are plain 0.x, without prerelease labels: `patch` for compatible changes (new airlines and assets, SVG fixes, additions to the API or data), `minor` for breaking changes to the API or the `airlines.json` shape. Run `npm run release -- [bump]` from a clean, up-to-date `main`; `bump` is `patch` by default, or `minor`/`major`/an exact version like `0.2.0`, and `--dry-run` previews. `scripts/release.js` tests the package, bumps the version in `package.json`, publishes to npm under `latest`, adds the airline slugs it shipped to `published-slugs.json`, on a minor release moves the release line links in `README.md` and `API.md` (`soaring-symbols@0.<minor>`, never exact releases) to the new line (`scripts/release-line.js`; `npm test` fails when one points at another line, and docs that only explain a line write `@0.<minor>`), commits `package.json`, `package-lock.json`, `published-slugs.json` and those docs as `chore(release): v<version>` and tags that commit `v<version>` (annotated), without pushing. Never run it unless the maintainer asks for a release.

Patch releases go out weekly, by hand, in a week with something users see since the previous tag (new airlines or marks, SVG or data fixes); a week without skips the release. `node scripts/release-notes.js` shows what is waiting. Breaking changes, above all removing an airline (`getAirline()` stops finding it and its files disappear from the release line), wait for the next minor release: their pull requests stay open with the `breaking` label, and a patch release may say in its notes that the removal is coming. The one exception is a takedown request (a trademark owner asking for its marks to go), which ships in the next patch with the reason in its notes. When `main` already holds a breaking commit (`!` or `BREAKING CHANGE`, which `release-notes.js` lists under Breaking changes), the next release is `minor`, never the default `patch`. Minor releases are rare, gathering what has waited, since each one moves the Raycast extension and the Figma plugin to a new release line ("Keeping releases compatible" in `AGENTS.md`).

Pushing the tag (`git push --atomic origin main v<version>`, the maintainer's call) runs `.github/workflows/release.yml`: it publishes a GitHub release titled `v<version>` with only a compare link to the previous tag (never touching a release that already exists) and, in a job of its own, purges jsDelivr's cache of the files changed since the previous release (`scripts/purge-cdn.js`). Nothing is released automatically or on a schedule; that is not decided yet.

Then release the draw.io libraries ([soaring-symbols/drawio](https://github.com/soaring-symbols/drawio)) from the version just published: `npm run release -- <version>` there publishes `@soaring-symbols/drawio` under the same version. It is done by hand for now; whether this workflow should trigger it, or a schedule there, is not decided ("Releasing automatically" in its README).

The release notes are written afterwards, when the maintainer asks. Start from the draft `node scripts/release-notes.js --to v<version>` prints (the commits since the previous tag, grouped into breaking changes, features, airlines and fixes) and rewrite it for readers of the package, the way the existing releases read:

- A one-sentence summary first, before any section: what is new for a patch ("Three new airlines: Air Arabia Abu Dhabi, Air Arabia Egypt and Air Arabia Maroc."), what breaks and what readers must do for a minor (the website's changelog shows it under the version, and feed readers see it first). Both show it as plain text, so it has no code, links or other Markdown: name paths in words ("the assets folder") and keep the details for the sections.
- `###` sections (Breaking changes, Features, Airlines, Fixes, any of them, in that order), one line per change described by its net result (an airline added and its data fixed in a later commit is one line, with its codes; a change made and undone is left out), PR numbers kept, but none under Airlines or Ecosystem, internal tooling only when contributors notice it, and the compare link last.
- An `### Ecosystem` section, after the others, for the major changes outside the package that come with the release's features, one line per app, for what users notice (no small fixes or polish). A package feature usually reaches the website and its API, the Raycast extension and the Figma, Framer and Webflow apps together, so their side of it goes in the notes of the release that ships the feature, even when it goes live a little later (update that release's notes then, not the next one's). The Raycast extension and the Figma and Framer plugins count once their update is published on their store, not while in review. Moving the apps to a new release line is not a change users notice, so a release with nothing else for them has no Ecosystem section. Each line starts with the app's name in bold and a colon (`- **Website**: …`, `- **Raycast extension**: …`) and says what changed in a short clause or two, with no links; only an app's first appearance links to where to get it (`- [Webflow app](…): …`).

Show the notes to the maintainer, then set them with `gh release edit v<version> --notes-file <file>`. Tags and GitHub releases start at v0.2.0: the `0.1.0-alpha` versions have none, and v0.2.0's notes sum up everything before it.

The purge compares the new release's published `dist/` with the previous one's, waits (up to 20 minutes; jsDelivr has taken six to seven) until jsDelivr resolves the release line (`@0.<minor>`) and the bare package to the new version, then purges each changed file under both, so links like `soaring-symbols@0.<minor>/dist/airlines/<slug>/logo.svg` serve the new file at once instead of after up to 12 hours; exact-release links never need it. A failed purge fails its job without touching the GitHub release: rerun the job, or run `node scripts/purge-cdn.js --since <previous version> [--version <version>]` from any checkout (`--dry-run` lists the files). Clients' own caches, such as a browser's or Raycast's, can still keep a line URL for up to 7 days, which is why the Raycast extension loads files from the exact release.
